# 2026-11-17 工作日志

## 任务：企业私有化、多租户、真开源云端 Agent 平台技术选型调研

用户想做"云端 agents 网站"，最终在企业内部私有部署、支持多租户。带了几个预设（Appwrite/Supabase 伪开源无意义、LobeHub 沙箱没开源、想基于 Codex 做多租户），要求全面调研真正开源可用的方案。

### 核心调研结论（均已联网 + 官方 LICENSE/文档核验，日期 2026-11）

- **Appwrite=BSD-3、Supabase=Apache-2.0**：真 OSI 开源，且都支持多租户（Appwrite Teams；Supabase RLS）。用户"伪开源没意义"判断不成立。局限在 open-core：SSO/审计在付费版。它们不是 Agent 平台。
- **LobeHub**：LobeHub Community License（Apache2.0+限制分发衍生作品，非 OSI）。默认沙箱是闭源云 market.lobehub.com（用户担心属实），但 v2.2.7 起可切 `SANDBOX_PROVIDER=onlyboxes` 开源自托管。不推荐作核心。
- **Open WebUI**：v0.6.6 起 BSD-3 加第4条品牌条款，非 OSI。Agent 是模型预设包装器+Open Terminal 沙箱；多用户/RBAC/SSO 开源，但多用户 Terminals 隔离属企业版。
- **★ AgentScope（阿里，Apache 2.0）= 首选**：六维全中。Runtime Sandbox 官方核验提供 Base/GUI/File/Browser/Mobile 沙箱，后端 Docker+gVisor/K8s/FC/ACK 全开源；`SandboxService` 用 session_id+user_id 原生多租户会话隔离；支持远程 sandbox server 与 MCP 暴露。短板：较新、社区小。
- **Bisheng 毕昇（Apache2.0 无附加）= 次选前端治理层**：开源版即 RBAC/SSO/审计，可改 LOGO 商用；沙箱较弱。
- Dify（Apache2.0+2限制，非OSI，CE单workspace多租户属EE；dify-sandbox 开源成熟）；Flowise 2026-08 已 EOL；n8n/FastGPT 非OSI；Langflow 无沙箱多次RCE。
- **Codex 设想**：Codex App Server 是真实组件（OpenAI 2026-02-04 官方博客），Apache2.0 开源在 `github.com/openai/codex` 的 `codex-rs/app-server`，是进程内 JSON-RPC over stdio 协议 + 长驻进程，非 HTTP 多租户服务。OpenAI 官方 Codex Web 架构=容器起 App Server+HTTP/SSE，与用户设想一致。但致命点：智能来自闭源云端 GPT-5/6 API，数据出企业；可配本地模型（model_provider/base_url/--oss）但能力下降。可行性评级：工程高/许可高/数据不出企业=低。

### 推荐方案

AgentScope Runtime（沙箱+多会话隔离核心）+ Bisheng 前端治理（RBAC/SSO/审计）+ Qwen/DeepSeek/gpt-oss + vLLM 自部署模型 + K8s/gVisor。落地三步：PoC(单机Docker跑通沙箱+user_id隔离) → 平台化(K8s+gVisor+SSO) → 生产化(限额/JIT密钥/审计)。风险：开源模型能力落差、沙箱必须内核级隔离防逃逸、社区较新。

## 需求澄清后的第二轮调研（重要：方向已改变）

用户在第二轮明确了真实需求，上一轮的"选 Agent 平台框架"方向是错的。真实需求：

- **做网页版 coding agent**（类 Trae 网页版 / Codex 网页版）：浏览器是瘦客户端，Agent 规划/模型/工具/代码执行**全在云端**。
- 用户已选：完整编码任务（读写仓库/装依赖/跑测试）+ 只需防互相干扰（内部可信员工，不用防逃逸）+ 100+ 并发 + 自研客户端可改造。
- 核心难题：**内网资源紧张，不能给每个用户起常驻 Docker**。真正的技术核心是"高密度多租户沙箱即服务"，不是 Agent 平台选型。
- 数据不出企业（内网自部署模型）。

### 第二轮核心结论（已官方核验）

- **最关键洞察**：资源瓶颈不在隔离技术，在"空闲会话常驻占内存"。Agent 会话 90% 时间在等模型/人。正解=让空闲会话**快照休眠、按需唤醒**，密度提升一个数量级。主流产品（Devin microVM 快照、Replit 预热池+CoW fork、Cloudflare DO 控制面+容器休眠）全这么做。
- **底座 = OpenHands**（官方核验 MIT LICENSE 原文）：有浏览器 Web UI（Agent Canvas，localhost:8000/canvas）+ Agent Server（REST 单机跑多 agent）+ 每会话独立 Docker 沙箱（`OH_CONVERSATION_RUNTIME=docker`）+ LiteLLM 接本地 vLLM/Ollama。几乎=开源版 Trae/Codex Web。短板：多用户治理(RBAC/SSO/审计)在 Enterprise 商业版，MIT 核心偏弱，需自研。
- **执行层两条路**：
  - 方案A（推荐先做）：普通 Docker + overlayfs 卷，`docker stop` 休眠/`start` 唤醒。对可信员工够用，纯 Docker 命令几天验证。
  - 方案B（进阶）：**Agent Substrate**（官方核验，CNCF Sandbox，Apache系）：gVisor 快照内存+磁盘、<500ms 恢复、>500 激活/秒、10x 容器密度、跑标准 K8s。**但它明确不支持普通容器，必须 gVisor/microVM**——对本案"过重"，真正值钱的是快照休眠调度器。
  - kubernetes-sigs/agent-sandbox（Apache-2.0，v1.0 2026-08，自带 WarmPool 预热池+Pod 快照，300 claims/s）作为平台化阶段的中间选项。
  - **避免 Daytona**：2026-06 核心闭源，末版 AGPL。
  - E2B runtime（Apache-2.0，支持 pause/resume/fork）可选作沙箱管理服务。
- **密度估算**（32核/64GB）：15-30 个活跃执行 + 500-2000+ 休眠会话（每快照几MB~几十MB）。100+ 并发会话用"20活跃+数百休眠+预热池"可扛住。
- 网络/状态：SSE 流式 + thread 状态存服务端（浏览器瘦客户端可断线重连）；休眠唤醒会断连需 SSE 重连续跑。

## 第三轮：用户质疑与方向最终收敛（决定性）

用户质疑：(1) OpenHands 缺陷是否被隐瞒、官网在哪；(2) 怀疑 Agent Substrate 不真实；(3) **关键新信息：企业内网 agent 客户端是基于 Codex App Server 实现，领导也要求走 Codex 路线，担心 OpenHands 不兼容**。

### 核实的事实（GitHub API + 官方文档，2026-11-17）

- **Agent Substrate 降级为观察**：创建仅 2026-05（半年）、7k star、1201 未关闭 issue。其"10x密度/<500ms"是 README 自述无第三方生产验证。用户怀疑正确，已从推荐移除。
- **真实成熟度数据**：OpenHands 93.6k star（2024，仓库从 All-Hands-AI/OpenHands 迁到 OpenHands/OpenHands）、Coder 17.4k（AGPL-3.0）、E2B 14.9k（Apache-2.0，agent沙箱事实标准，Pause/Resume 已上线稳定）、Gitpod 13.8k、agent-sandbox 4.6k（K8s官方SIG，Apache-2.0）。
- **OpenHands 真实缺陷**（评测有据）：免费版 Agent Canvas 是 single-user shared identity，多用户 RBAC 在付费 Teams/Enterprise；Docker 硬依赖需挂 docker.sock；每容器约 4GB+ RAM；镜像 tag 强耦合；<30B 本地模型会循环/幻觉/谎报完成；token 烧得快；git 凭据处理差；工具调用默认 30s 超时。官网 openhands.dev（Cloud 免费10对话/天），自部署看 SELF_HOSTING.md。
- **决定性发现**：OpenHands 官方 README 原文支持 "Codex, Claude Code, or any ACP-compatible agent" 作为后端——即 OpenHands Agent Canvas 可作网页壳、Codex 作 agent 引擎，二者不冲突。但据此前调研，Codex CLI 走 ACP 集成，用户用的是 App Server（JSON-RPC over stdio），二者能否直接对接需实测，无官方确认。

### 用户确认的两个地基前提（AskUserQuestion）

1. **模型接入 = 已接内网自部署模型**（通过 model_provider/base_url 指向内部 vLLM，数据不出企业）→ 推翻之前"Codex 依赖闭源云端模型"的顾虑。Codex harness 全 Apache-2.0 开源，整套真开源可私有部署。
2. **Codex 形态 = 官方 codex CLI 的 -s app-server 模式**（开源仓库 app-server 组件）。

### 最终方案（方向收敛）

不需要换 Agent 引擎——领导要 Codex、用户已有 Codex，就用 Codex。OpenHands 不做 Agent 层（多租户要付费，反添乱）。真正要补的只有三块：
- ① 网页前端（浏览器开会话、SSE 流式）— 可复用开源 Chat UI 或自研
- ② 多租户网关（鉴权/用户-会话映射/配额/HTTP↔App Server JSON-RPC 转换）
- ③ 云端执行层（每会话一沙箱容器 + 休眠复用，E2B 或 K8s agent-sandbox）

架构直接照抄 Codex Web 官方：worker 起容器→容器内跑 App Server→浏览器经 HTTP/SSE 连后端→thread 状态服务端持久化。关键认知：App Server 是进程内 stdio 协议，不带 HTTP 鉴权/多租户/沙箱调度，这些都要自研网关层。
