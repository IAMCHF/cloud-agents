# 2026-11-18 P1 冷恢复实验（销毁→新沙箱挂卷→thread/resume）

一次性记录。对应实施计划 §7 L4，验证密度模型核心假设（方案 C4）：空闲会话可销毁容器、
只留卷，回来时新沙箱挂卷 + 原生 `thread/resume` 恢复。结论：**冷恢复可行（PASS）**——
全新 codex 进程从卷上状态回放历史并真实续聊，恢复耗时秒级（开发机：建沙箱 5.5s + resume 0.67s）；
但 **P1 现状不支持**（CODEX_HOME 容器内 + 新会话新卷 + 会话与沙箱生命周期耦合），产品化属 P3，缺口清单见下。
本次**零代码改动**，实验脚本一次性不入库（`.local/`，gitignore）。

## 环境与版本

- 开发机 Windows + Docker Desktop（非内网执行机）；OpenSandbox `uvx opensandbox-server` Docker 运行时，
  execd v1.1.0、egress sidecar v1.1.7（`mode="dns+nft"`）。
- 控制面 `feat/p1-poc`（90858df，egress 关闭提交后未改代码）；SQLite 台账 `.local/ledger.db`。
- 沙箱镜像 `cloud-agents/sandbox:0.1.0`（codex-cli 0.167.0，Debian 12）；模型 DeepSeek `deepseek-flash`（公网 Responses API）。
- 卷：host bind mount `<WORKSPACE_HOST_ROOT>/<session_id>` → `/workspace`（P1 单卷形态）。

## 实验设计（两腿）

- **leg1 现状腿**：走 P1 正常流程。会话 A 建线程跑真实 turn → 把 marker 文件与 CODEX_HOME
  手工落到会话卷（`cp -a /home/agent/.codex /workspace/.codex`）→ DELETE A（卷保留）→
  新会话 B 对 A 的线程 `thread/resume`。**预期失败**，证明现状缺口。
- **leg2 可行性腿**：绕开 P1 编排，手工经 OpenSandbox API 建恢复沙箱 R：
  - `entrypoint=["sleep","infinity"]`（不起桥接），codex 由 `docker exec -i sandbox-R codex app-server`
    以 stdio NDJSON 直接驱动——**全新进程**，排除「同进程缓存」假象。
  - 挂两个卷：A 的会话卷 → `/workspace`；`<A卷>/.codex` → **原容器路径** `/home/agent/.codex`
    （codex 状态库含绝对路径，挂回原路径避免 rollout 路径失配）。
  - env 注入 `CODEX_HOME`、`OPENAI_BASE_URL=<网关>/llm/v1`、`OPENAI_API_KEY=<B 的会话 token>`
    （网关鉴权锚点：R 不是控制面会话，借存活会话 B 的 token 过网关）、模型档位与 A 一致。
  - `networkPolicy` 默认 deny + 放行网关主机；资源限额 2 CPU / 2Gi。
  - 验证：marker 可读 → initialize → `thread/resume`（历史含 baseline 回复）→ 真实续聊 turn。

## 验证项与证据

### 1. 基线与状态落卷（leg1 / A）

- A：session `s-298dd1f2…`，sandbox `d5b4b11d…`；`turn/start` 1.1s 回复 `baseline-ok`（真实模型）。
- `echo cold-recovery-marker > /workspace/marker.txt` 成功；`cp -a` 后卷上 `.codex` 含
  `state_5.sqlite`、`thread_history_1.sqlite`、`sessions/`、`config.toml` 及各 `-wal/-shm`。
- 线程 ID `01a1edf1-96b1-7762-8b27-e0db075897fb`。

### 2. 销毁后现状缺口实锤（leg1 / B）

- DELETE A → 204；host 卷目录保留（`volume kept: True`）。
- 新会话 B（新沙箱、新卷）`thread/resume` 立即失败（0.0s）：

```
{"code": -32600, "message": "no rollout found for thread id 01a1edf1-96b1-7762-8b27-e0db075897fb"}
```

原因与代码分析一致：CODEX_HOME 在容器内随销毁丢失；B 挂的是自己的新卷；台账/Hub 无跨沙箱恢复路径。

### 3. 新沙箱挂旧卷恢复（leg2 / R）

- R sandbox `f15d6ca7…` 创建→Running **5.5s**；`cat /workspace/marker.txt` → `cold-recovery-marker`；
  `/home/agent/.codex` 可见 A 的全部状态文件。
- 全新 codex `initialize` 正常（0.167.0）；`thread/resume` **0.67s** 成功，响应 2645 字节，
  **历史回放含 `baseline-ok`**。
- 续聊 `turn/start`（"Reply with exactly: resumed-ok"）**1.3s** 回复 `resumed-ok`；
  控制面日志同期 `POST /llm/v1/responses 200`——续聊确实经 LLM 网关、以 B 的会话 token 鉴权。

### 4. 清理与台账

- R 经 OpenSandbox DELETE → 204；B 经控制面 DELETE → 204；A 卷仍保留（marker + `.codex` 均在）。
- `docker ps` 无残留沙箱/sidecar 容器；台账 A/B 均 `ended`。

**[RESULT] cold recovery PASS（resume 0.67s）。**

## 发现的缺口与 P3 产品化清单（本次不改代码）

1. **状态盘放置**：CODEX_HOME 当前容器本地（`/home/agent/.codex`），须落会话卷（或销毁前归档到卷）。
   实验用手工 `cp -a` 替代。
2. **会话与沙箱/卷解耦**：新会话固定新卷路径（`<root>/<session_id>`）；桥接断开即 `mark_ended` + `hub.remove`。
   跨沙箱恢复需要「逻辑会话 → 会话级卷」的稳定映射与恢复编排（建新沙箱挂旧卷、注入新 token、代客户端 `thread/resume`）。
3. **快照一致性**：`cp -a` 在 codex 运行时复制了 SQLite WAL/SHM，本次 resume 成功但存在撕裂写风险；
   产品化应在销毁前停写/`wal_checkpoint`（codex 正常退出即落盘）。
4. **恢复沙箱的网关鉴权**：实验借存活会话 B 的 token；P3 需为恢复路径设计 token 签发/换绑（属管理面，不涉执行协议）。
5. **小观察（不影响结论）**：DELETE 触发的桥接断开回调与 `stop_session` 的 `mark_ended` 竞态，
   台账 `end_reason` 记为 `sandbox_exited` 而非 `stopped`；客户端 WS 早于桥接就绪连接会收 1013，需重试（Web 已有重连逻辑）。

## 未覆盖风险

- 仅 1 轮历史的小线程；长线程/大状态库的 resume 耗时与网关回放体积未测（L6 基准一并覆盖）。
- NFS 卷上恢复未测（L5，内网执行机就绪后）；跨主机恢复依赖共享存储，本机 host 卷不代表内网形态。
- 并发恢复、预热池取沙箱的端到端时延未测（P3）。
- codex 版本升级可能改状态格式，pin 变更须复跑本实验。

```jsonc
// leg2 恢复沙箱创建 payload（OpenSandbox POST /v1/sandboxes）
{
  "image": {"uri": "<沙箱镜像>"},
  "entrypoint": ["sleep", "infinity"],
  "env": {"CODEX_HOME": "/home/agent/.codex", "OPENAI_BASE_URL": "<网关>/llm/v1",
          "OPENAI_API_KEY": "<存活会话 token>", "CODEX_MODEL": "<同 A>", "...": "档位同 A"},
  "volumes": [
    {"name": "workspace",  "mountPath": "/workspace",          "host": {"path": "<A 会话卷>"}},
    {"name": "codex-home", "mountPath": "/home/agent/.codex",  "host": {"path": "<A 会话卷>/.codex"}}
  ],
  "networkPolicy": {"defaultAction": "deny", "egress": [{"action": "allow", "target": "<网关主机>"}]},
  "resourceLimits": {"cpu": "2", "memory": "2Gi"}, "timeout": 3600
}
```

leg1 走控制面 REST + WSS（`POST /api/sessions` → `initialize`/`thread/start`/`turn/start` →
`docker exec` 落 marker 与 `.codex` → DELETE → 新会话 `thread/resume` 预期 -32600）；
leg2 用 `docker exec -i sandbox-R codex app-server` stdio 驱动 `initialize`/`thread/resume`/`turn/start`。
