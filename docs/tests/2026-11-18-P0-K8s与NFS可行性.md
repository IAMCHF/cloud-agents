# 2026-11-18 P0 开发机可行性验证（K8s / NFS / OIDC）

P0 目标：在开发机搭出接近内网的本地模拟，验证运行时、存储、身份三条路径的可行性，
为 P2/P3/P4 的架构决策提供证据。结论：**K8s 运行时可用，但 pause 依赖 snapshot registry；
HA 台账必须用 Postgres；OIDC 本地可闭环；P3 冷恢复优先于快照暂停。**

## 环境

| 项 | 值 |
|---|---|
| 宿主 | Windows + Docker Desktop，12 CPU / 15.54GiB |
| 本地集群 | kind 0.33.0，Kubernetes v1.37.0，1 control-plane + 2 workers |
| 包管理 | Helm 3.17.3（Windows 侧） |
| OpenSandbox | charts `release-1.2.1`：base / controller / ingress-gateway / server；镜像来自阿里云 registry |
| 沙箱镜像 | `cloud-agents/sandbox:0.1.0`，`kind load docker-image` 注入节点 |
| NFS | `itsthenetwork/nfs-server-alpine:12`，Docker NFSv4 卷 |
| OIDC | Keycloak 26.4（dev 模式，realm `cloud-agents`） |

## 1. K8s 运行时

安装顺序与结果：

| 步骤 | 结果 |
|---|---|
| `base` chart（CRD + RBAC） | 通过；CRD `batchsandboxes` / `pools` / `sandboxsnapshots` 均已安装 |
| `opensandbox-controller` | Running |
| `ingress-gateway` | Running（kind 无 LoadBalancer，P0 不使用） |
| `opensandbox-server` | Running，`/health` 正常；K8s 内建 runtime 生效 |
| 创建沙箱 | `POST /v1/sandboxes` 返回 202，BatchSandbox → Pod `1/1 Running` |
| exec | Pod 内 `id` = uid 1000，Debian 12；`kubectl exec` 正常 |
| 资源限额 | Pod `requests=limits`：cpu 1 / memory 1Gi；limit 精确落到容器 |
| 销毁 | `DELETE` 返回 204，BatchSandbox 与 Pod 全部回收 |
| Entrypoint | 实际命令为 `/opt/opensandbox/bootstrap.sh sleep 600`（bootstrap 包装 + execd 初始化） |

**Pause/resume（关键发现）**：`POST /pause` 返回 202，但 controller 的 `SandboxSnapshot`
失败：`snapshot-registry not configured in controller manager`，BatchSandbox 进入
`PauseFailed/SnapshotFailed`，Pod 保持 Running；随后 `resume` 返回
`KUBERNETES::INVALID_STATE: Cannot resume sandbox in state Running, expected Paused`。

结论：**K8s 的 pause 不是 Docker 式的进程暂停，而是容器镜像快照，必须有 registry +
image-committer + controller 的 snapshot 配置**。P3 优先采用“销毁 Pod + 工作区卷持久化 +
冷启动”的既有冷恢复路线，避免引入镜像快照链路；若后续确需快照恢复，再单独立项。

**安全差异**：K8s 运行时的 Pod `securityContext` 为空，Docker 路径上的
`no_new_privileges`、cap drop 不会自动带过去。P4 必须在 BatchSandbox 模板/部署清单补
`runAsNonRoot`、`allowPrivilegeEscalation=false`、`drop: [ALL]`、seccomp。

**Egress**：带 `networkPolicy` 创建的沙箱为 `2/2`（sandbox + egress sidecar），sidecar env
含 `OPENSANDBOX_EGRESS_RULES` 与 `OPENSANDBOX_EGRESS_MODE=dns+nft`。Pod 内实测：

- `1.1.1.1:443` → CONNECTED（显式 allow）
- `8.8.8.8:443` → TimeoutError（默认拒绝）
- `example.com` / `api.deepseek.com` DNS → BLOCKED

K8s egress 与 Docker 路径行为一致，可用于 P4。

## 2. NFS 上的 SQLite（L5）

NFSv4 卷挂载到多个容器，两个独立客户端并发访问：

| 场景 | 结果 |
|---|---|
| WAL 初始化 + 两个客户端各写 100 行 | 200 行落库，`integrity_check=ok` |
| DELETE journal：A 持写锁 3s，B 等待 | A 实际 6.36s 提交，B 等待 5.46s 后获得锁 |
| WAL：A 持写锁 3s，B 等待 | A 3.01s 提交，B 等待 2.08s 后获得锁 |
| 两个客户端各 50 个文件 create/rename/fsync | 100 个文件，全部成功 |

结论与限制：

- **同一内核/同一宿主**下 NFSv4 的锁与 WAL 可用，但延迟明显高于本地盘。
- 跨主机 WAL 未验证，且 SQLite 官方要求 WAL 依赖共享内存（`-shm`），**不能假定多主机 NFS 安全**。
- 因此：P2 HA 的台账必须用 Postgres（控制面已支持 asyncpg）；SQLite 只允许单节点部署。
- 沙箱工作区是单写者场景，NFS 文件操作可用；真实 NAS 的 UID/GID、权限、性能和断连恢复留 D2。

## 3. OIDC（Keycloak）

- realm `cloud-agents` 导入成功；`/.well-known/openid-configuration` 返回 issuer、授权/令牌/JWKS 端点。
- 机密客户端 `cloud-agents-svc`（service account）走 `client_credentials` 成功：

- Web 公共客户端 `cloud-agents-web` 已配置 PKCE 授权码回调 `http://127.0.0.1:5173/*`。
- 真实内网 IdP 的 claim/组映射与注销行为留 D2。

## 4. 开发机环境问题（非产品缺陷）

| 问题 | 处理 |
|---|---|
| Windows 稀疏检出 CRLF 导致 Helm 的 `splitList "\n---\n"` 只渲染首个 CRD | 手动 `kubectl apply -f charts/base/files/crds.yaml`；Linux 检出不受影响 |
| GitHub release 下载慢 | 镜像 `ghfast.top` / `docker.1ms.run`；镜像统一走本地可拉取地址 |
| 端口转发随 PowerShell 会话退出 | 用受控后台进程跑 `kubectl port-forward` |
| kind 节点共享 Docker Desktop VM，`capacity` 显示宿主机规格 | 本地按缩比 N 验证，目标规模留 D2 |

## 6. 决策与下一步

1. **运行时**：K8s 作为一等后端可行；进入 P1.5，先做运行时/存储抽象与 `pvc` 落地，
   再把控制面 + 桥接 + 真实 turn 完整跑在 kind 上（当前 `volume_backend=pvc` 仍会报错）。
2. **暂停**：P3 用冷恢复（销毁 + 卷持久化 + 重建），不引入 snapshot registry；快照方案留待明确需求。
3. **台账**：HA 场景固定 Postgres；SQLite 仅单节点。
4. **OIDC**：P2 用 Authlib 接 Keycloak discovery；真实 IdP 作为 D2 首项。
5. **安全**：P4 部署清单必须显式补 Pod securityContext 与 NetworkPolicy 基线。

复跑入口：kind 集群、OpenSandbox charts、Keycloak 与 NFS 均为开发机工具，命令与 values
见本记录；不进入仓库依赖。
