## 1. 控制面加固（已应用并验证）

`deploy/k8s/control-plane.yaml`：

```yaml
securityContext:            # Pod
  runAsNonRoot: true
  runAsUser: 1000
  runAsGroup: 1000
  fsGroup: 1000
  seccompProfile: {type: RuntimeDefault}
containers.control-plane:
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities: {drop: ["ALL"]}
  volumeMounts: [/archive(PVC), /tmp(emptyDir)]
  env: HOME=/tmp
initContainers.wait-postgres:
  allowPrivilegeEscalation: false
  capabilities: {drop: ["ALL"]}
```

## 2. 沙箱容器加固（模板已交付，待执行节点验证）

新增 `sandbox/opensandbox/batchsandbox-template.yaml`：给 `sandbox` 容器补
`runAsNonRoot/runAsUser=1000/allowPrivilegeEscalation=false/readOnlyRootFilesystem=true/drop ALL/seccomp=RuntimeDefault`，
并用 memory emptyDir 挂 `/tmp`；egress sidecar 保留其必需的 `NET_ADMIN`。

为什么不直接套 Pod Security Admission `restricted`（kind 实测 Pod spec）：

- OpenSandbox 生成的 Pod 含 **privileged initContainer**（拷贝 execd/bootstrap）；
- egress sidecar **add NET_ADMIN**；
- 两者都会被 restricted 拒绝。因此只能在 BatchSandbox 模板中按容器加固，或换用更细的准入策略。

启用步骤（部署操作者）：

1. 将模板挂载到 opensandbox-server（ConfigMap/宿主机文件）。
2. `config.toml` 设 `[kubernetes] batchsandbox_template_file = "/etc/opensandbox/batchsandbox-template.yaml"`。
3. 重启 server，新建沙箱后 `kubectl -n opensandbox get pod <id>-0 -o yaml` 确认 `sandbox` 容器
   securityContext 与 `/tmp` 挂载已合并；若未合并，说明该 server 版本不按容器名合并，需要
   升级 OpenSandbox 或改集群准入策略。
4. 回归 T1–T6：建会话、真实 turn、终端、文件树、预览、冷恢复、归档。

## 3. gVisor 评估（未安装）

- 现状：隔离边界是容器；codex 以 `danger-full-access` 在容器内运行（无嵌套 bwrap），容器逃逸可直达用户卷。
- gVisor 无 KVM 依赖，适合内网 VM；但需要执行节点的 containerd 安装 `runsc` 并注册 RuntimeClass，
  属节点级变更，kind 开发集群不具代表性。
- 兼容性风险：codex 可能触发 gVisor 未实现的 syscall/ptrace 行为；git/npm 构建负载需实测。
- 建议：D2 在执行节点安装 runsc → 模板加 `runtimeClassName: gvisor` → 复跑 T1–T6 金路径与
  `bench/load.py density --sessions 8`，对比创建时延/turn 时延/CPU；无回退需求前不默认开启。
