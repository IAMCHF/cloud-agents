## 1. 技术栈（2026-11-17 拍板）

原则：全部 OSI 许可（Apache/MIT/BSD 优先），成熟生产验证；P1 只引最小集，按阶段引入。控制面 Python + FastAPI，Web React + TypeScript；UI 用 Tailwind + 自绘聊天层（2026-11-18 修订：assistant-ui 0.15 换用 Aui store API 且 Thread 组件拆到独立包，与客户端 0.11 系不同，P1 不引、P3 评估迁回；仍弃 shadcn/ui），Python 包管理定 uv。

**控制面（Python ≥3.12）**

| 用途 | 选型 | 许可 | 阶段 |
|---|---|---|---|
| HTTP/WSS 入口 | FastAPI + uvicorn（WebSocket 用 Starlette 原生） | MIT / BSD-3 | P1 |
| 配置/信封校验 | Pydantic v2 + pydantic-settings（密钥走环境变量） | MIT | P1 |
| 异步 HTTP | httpx（LLM 网关流式转发 + OpenSandbox API） | BSD-3 | P1 |
| 沙箱侧桥接 | websockets + asyncio subprocess（stdio↔WSS） | BSD-3 | P1 |
| 台账/审计 | SQLAlchemy 2.0 async + asyncpg + Alembic | MIT / Apache-2.0 / MIT | P1 |
| 租户/RBAC/配额 + OIDC | 同上库表 + Authlib | BSD-3 | P2 |
| 埋点/日志 | prometheus-client + structlog（活跃率实测；审计落 Postgres） | Apache-2.0 / MIT·Apache | P1 |
| 调度 | 进程内 asyncio + Postgres 台账，不引 Celery/Redis；P1 单 uvicorn worker（进程内状态） | — | P1；P2 HA 需会话路由设计（sticky 或 Postgres pub/sub） |
| 工程化 | uv + Ruff + mypy + pytest / pytest-asyncio | MIT·Apache / MIT / MIT / MIT·Apache | P1 |

LLM 网关对沙箱暴露 OpenAI 兼容接口（codex `model_providers` 原生支持），真 key 只在网关；内网模型服务适配按实际协议定（对接由用户操作）。**P1 即需最小转发代理**（httpx SSE 透传、无计量，落 `app/llm_gateway`），否则金路径无 LLM 可走；P2 补计量/配额/审计增强。网关 P1 虽无计量仍须校验会话 token；token/URL 经 env/tmpfs 注入不落持久卷。控制面同时承担 150 路 LLM SSE 转发，是流量咽喉，HA/扩容单独考虑（见 §2）。

## 2. 资源预算（500 在线用户）

**前提：资源 = 峰值并发活跃会话 × 单沙箱开销。活跃率规划值 30%（150 并发），PoC 后实测回调。**

单活跃沙箱：内存均值 0.5GB / cgroup 硬限 2GB；CPU 均值 0.3 vCPU / 硬限 2 vCPU；用户卷 2–5GB。

| 角色 | 规格 | 数量 | 说明 |
|---|---|---|---|
| 执行节点 | 16 vCPU / 64GB / 200GB SSD | 3 | 48 vCPU / 192GB，承载 150 活跃（均值 45 vCPU / 75GB）。**CPU 是紧维度**：均值 45/48≈94%，突发余量有限；N-1 剩 32 vCPU 承不住 45 均值，故障须降并发准入。极限 500 活跃按 0.3 vCPU 均值需约 10 台（150/16），非 6–8 |
| 控制面 | 4 vCPU / 8GB | 2 | HA；负载含 500 客户端 WS + 150 桥接 WS + **150 路 LLM SSE 转发** + 审计写入，非仅长连接，网关转发是咽喉；P1 单 worker，HA 路由 P2（见 §1 调度） |
| 共享存储 | NAS/NFS 1–2TB | — | 500 用户工作区卷；按 5GB/用户上限达 2.5TB，超预算上限，须配卷配额 + 归档清理（P3） |
| 数据库 | Postgres 17，4 vCPU / 8GB | 1（P1） | P1 与控制面共置单机；P2 HA 需独立规格与主从/备份；台账 + 全量审计写入吞吐见 §5 |

合计约 **56 vCPU / 208GB / 2TB**（P1 单机 PoC 远低于此）。极限（500 全活跃）按 CPU 均值需执行节点扩至约 10 台，横向加机即可；CPU 均值若实测更低可下调。

边界：
- **LLM 推理另核**（通常是最大成本项）：向模型服务方确认 150 路并发流的容量余量。
- 密度模型成立前提：每沙箱 cgroup 硬限 + 租户并发配额 + **总量准入**。**cgroup 硬限只约束单沙箱，防不了总量超卖**：150×2GB 硬限=300GB 已超 192GB 物理内存，宿主仍会 OOM。max_active_sessions 须按总量预算取值——保守上界按硬限取小（CPU 48/2=24、内存 192/2≈96 → 24），或按均值+余量（规划 150，接受 OOM 风险）。**P1 无租户配额（P2），先设全局 max_active_sessions**（超限排队/拒绝），PoC 取保守值并按实测回调；OOM 被杀 ≈ 逻辑冻结，靠 resume 恢复（打断进行中 turn）。调度准入按总量预算而非瞬时 free（P2）。

## 3. 实施阶段

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| P1 PoC（1–2 周） | 单机 Docker + OpenSandbox；沙箱内 codex app-server ↔ stdio 桥接 ↔ WSS ↔ 最小网页；LLM 走内网网关 | 金路径：网页派真实 coding 任务 → 流式回显 → 审批弹窗 → 关页重开 resume 成功；**交付活跃率埋点能力 + 模拟负载基准**（真值需上线后观测，30% 规划值据此回调）；冷恢复实验（销毁→挂卷→resume）+ NFS SQLite 锁实测 |
| P2 控制面 | OIDC、会话台账、调度器（按总量准入预算 + 节点余量，非瞬时 free；多客户端扇出/仲裁设计）、LLM 网关计量、配额、HA 会话路由 | 多租户并行任务互不干扰；配额/审计生效 |
| P3 密度与体验 | 预热池、空闲销毁策略、卷归档；Web 补齐 diff 审查/任务列表/终端/文件树/预览 | 150 并发压测通过；空闲会话零计算占用 |
| P4 加固与接入 | egress 策略全量、客户端档位 A/B 接入、（可选）gVisor、K8s 运行时迁移 | 客户端零/低改动接入验收；安全评审通过 |

工作量估计：控制面+桥接 2–3 人月；Web 前端 1–2 人月；执行层用现成组件不自研。

## 4. P1 任务拆解（2026-11-17 修订）

分支 `feat/p1-poc`；一任务一提交，依赖顺序执行。验收总标准 = §3 P1 金路径 + 活跃率埋点。

| # | 任务 | 交付 | 验证 |
|---|---|---|---|
| T1 | 工程化底座 | control-plane/pyproject.toml（uv + P1 最小依赖集 + Ruff/mypy/pytest）；web/package.json（Vite + React 19 + TS + Tailwind 4 + assistant-ui + Zustand + Biome + Vitest）；模块级 AGENTS.md（control-plane/、web/）；pre-commit 门禁 + 覆盖率/jscpd 配置；AGENTS.md 补齐构建/测试命令 | lint/类型/测试全绿 |
| T2 | 协议绑定 | pin codex 版本（版本号记入本文档）；`generate-json-schema` 产物入库 + json-schema-to-typescript 生成 TS 绑定入 web/src/codex/ + CI 漂移校验（与客户端 generate-codex-schema 同流程；客户端脚本为 PowerShell+Windows 二进制，云端 CI 需跨平台重实现，对 pin 的 Linux 二进制核实子命令与产物格式） | 绑定与 pin 版本一致 |
| T3 | stdio↔WSS 桥接 | app/bridge/：沙箱侧桥接进程（websockets + asyncio subprocess）+ 控制面 WSS 端点；原生 JSON-RPC 薄信封透传；背压/断线缓冲；fake codex app-server（脚本化 JSON-RPC 应答进程）供集成测试 | 单测+集成：双向帧转发/审批回调/断线重连 |
| T4 | 沙箱生命周期+最小网关 | app/sandbox/ OpenSandbox 客户端；启动时序：创建→挂卷（会话级子目录）→注入会话 token 与控制面地址（env/tmpfs，不落持久卷）→起 bridge→bridge 拉起 codex（bridge 代码打包进镜像）；codex 退出上报与重启策略；app/llm_gateway/ 最小 SSE 转发（无计量，校验会话 token）；全局 max_active_sessions + 同用户单活跃准入；P1 egress 白名单（控制面/网关/内部 git/包镜像）；sandbox/images/ Dockerfile（Debian slim、codex pin、非 root、只读 rootfs + /tmp/缓存 tmpfs、cgroup 限额、NFS uid 映射）；sandbox/opensandbox/ 配置；最小会话台账 + 事件审计落库（SQLAlchemy + Alembic，批量/异步写） | 创建/销毁/resume 冒烟；OpenSandbox API 不符则按边界回退裸 Docker SDK |
| T5 | 最小 Web | src/rpc/ WSS 客户端；src/features/ 对话流/审批/resume——从 yice-agent 拷贝 ApprovalCard、MarkdownContent、VirtualContent 等组件**及其测试**，适配 Codex 绑定类型 | Vitest 全绿 + Playwright 金路径（mock 模式） |
| T6 | 埋点与编排 | prometheus-client 活跃会话指标；Compose 单机编排（Postgres 17 + 控制面 + OpenSandbox）；健康检查/优雅停机/CORS；WSS TLS 终结位置按部署定 | 指标端点出数 + Playwright 金路径报告 |

P1 鉴权：环境变量简单 token 标识会话属主（P2 换 OIDC）；沙箱桥接连接用会话级 token。**P1 resume 语义 = 重连同一沙箱 + `thread/resume`**（空闲销毁在 P3，跨沙箱挂卷恢复属 P3）；审批重放由桥接缓存 pending 请求实现（同沙箱重连 stdio 不断；「app-server 原生重放」待核实）。PoC 实测项：活跃率埋点 + 模拟基准、**冷恢复实验**（销毁→新沙箱挂卷→thread/resume，测真正贵的恢复路径）、**NFS 上 codex 状态库（SQLite）锁兼容性**（不可行则状态盘本地化+卷归档或换卷方案）、OpenSandbox Docker 模式能力（pause 语义/热挂卷/egress/execd）。不做：OIDC/配额（P2）、预热池/空闲销毁（P3）、diff/终端/文件树（P3）、egress 全量策略（P4，**P1 放行控制面+网关+内部 git+包镜像四类**）、客户端 shim（P4）、多客户端同时在线（P2+）。

**codex pin：`0.167.0`**（2026-11-18 落定，与客户端 yice-agent `src-tauri/protocol/codex-version.txt` 一致）。已实测：win32-x64 与 linux-x64（musl）二进制生成的 37 个顶层 schema **逐字节一致**；生成脚本 `scripts/codex-schema.mjs`（Node，跨平台），产物 `web/src/codex/schema/` + `web/src/codex/generated/`，漂移校验 `pnpm check:codex` 已进 `pnpm run check`。v1/v2 子目录（283 个分方法 schema）暂不入库，需要时用生成脚本取。

用户操作项（AI 只给步骤与验收并复查）：内网执行机/Docker/OpenSandbox 部署、LLM 网关对接与密钥、codex 二进制获取（内网镜像不可达时由用户提供）。**待决环境项**：AI 跑 Docker 冒烟/E2E 真模式的机器（本机 Docker Desktop 或内网执行机）；CI 平台（内网 Git?）。**进度风险**：真模式金路径依赖上述用户操作且待决，1–2 周估计的最大不确定性是环境就绪而非代码；环境未就绪时 P1 先交 mock 链路全绿。
